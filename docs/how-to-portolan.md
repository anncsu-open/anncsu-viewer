# Portolan catalog for the ANNCSU dataset

## Goal

Publish the ANNCSU address dataset as a [Portolan](https://github.com/portolan-sdi/portolan-spec)
catalog so the data is discoverable through STAC, with metadata that a validator can check and an agent can read.

The catalog is generated by the data pipeline and published to the same
Cloudflare R2 bucket that already serves the data. Metadata lives in git, so the catalog gets version history, rollback, and a pull-request contribution path without a second repository.

## Decisions

| Question | Decision |
|---|---|
| Where the catalog lives | Generated into `data/`, inside `anncsu-viewer`, not a separate repo from the Portolan template |
| Href style | Relative, with an absolute `self` link on the root |
| Collections | Two: `indirizzi` (single-file) and `indirizzi-h3` (partitioned) |
| Primary language | Italian |
| Providers | Mixed: `anncsu-open` as processor, Geobeyond as host |
| Build trigger | A separate GitHub Actions workflow, downstream of "Update ANNCSU Data" |
| `partition:glob` scheme | HTTPS, with the tile index documented as the expansion path |

### Why not the Portolan catalog template

The template gives CI, a publish guard, and a contribution path. All three are
worth having, but the template also assumes the catalog is built by hand and
published on its own schedule. Here the catalog is a derivative of a pipeline
that already runs monthly, already computes every number the catalog needs, and
already uploads to the bucket. A second repository would need a cross-repo
trigger and would let metadata drift from the data it describes.

The parts of the template that carry their weight are reproduced: `rashid` runs
as a CI gate, and the upload step is scoped to catalog paths only.

## Published layout

`data/` is already a 1:1 image of the bucket root, so the catalog is generated
there and the existing rclone step publishes it.

```
data/                                  = https://pub-1e760dc850cb4a5aa5f8afb77713f8cd.r2.dev/
├── catalog.json                       generated
├── README.md                          generated from template
├── AGENTS.md                          generated from template
├── anncsu-indirizzi.parquet           existing, 1009.9 MB
├── anncsu-indirizzi.pmtiles           existing, 317.7 MB
├── comuni.json                        existing
├── comuni-h3.json                     existing
├── tiles/h3_cell=*/*.parquet          existing, 1348 files
├── indirizzi/
│   ├── collection.json                generated
│   ├── README.md                      generated
│   ├── AGENTS.md                      generated
│   ├── thumbnail.png                  generated
│   └── styles/indirizzi.json          copied from source
└── indirizzi-h3/

```

Data files stay where they are. Nothing moves, so the frontend, the rclone sync, and every published URL keep working.

Hand-written sources live outside `data/`, in `scripts/catalog/`:

- `columns.yaml` gives each column a type and an Italian description. It feeds
  both `table:columns` and the schema table in the generated READMEs, so a
  description is written once.
- `*.md.tmpl` are the README and AGENTS templates, filled with
  `string.Template` from the standard library. No template engine, and `$`
  placeholders avoid clashing with the braces in JSON examples.
- `styles/*.json` are the MapLibre GL style files, copied verbatim into the
  published tree.

## The generator

`scripts/build_catalog.py`, a PEP 723 script depending on `duckdb`, `pyyaml`,
`pmtiles`, and `pillow`. It is standalone and file-driven: it reads `data/` and
`scripts/catalog/`, never the pipeline's in-memory state. It can be re-run at
any time without re-downloading anything.

| Value | Source |
|---|---|
| Row count, bbox, column schema | DuckDB over the parquet |
| `file:size`, `file:checksum` | Bytes of the parquet and the PMTiles |
| PMTiles layer name and zoom range | PMTiles header, read with the `pmtiles` library |
| Tile count and partition key | Glob over `tiles/h3_cell=*/*.parquet` |
| Dataset date | `data/.last_remote_date` |
| `updated` | Commit date of the last commit touching the parquet |

### Determinism

`updated` comes from the data commit date rather than the wall clock. The
generated tree is therefore byte-identical when the data has not changed, so a
workflow run over unchanged data commits nothing and uploads nothing.
`PORTO-CORE-057` asks for the time of the sync, and the data commit is exactly
that.

Output is written atomically, with a temporary file and a rename, and JSON keys
are emitted in a stable order.

### Thumbnail

`PORTO-CORE-067` requires a thumbnail generated from default styling. The
generator aggregates the 20.7M points into a grid of roughly 800x900 cells over
the dataset extent with DuckDB, then renders a PNG with Pillow using the colour
from the default style. It is a density image, not a MapLibre screenshot, which
keeps the build free of a headless browser. Both collections share the image,
because they describe the same data.

### Column drift

`columns.yaml` is the single source of truth for descriptions. The generator
compares its names against the real parquet schema and fails when a parquet
column has no description, or when the YAML describes a column that no longer
exists. An upstream schema change cannot pass silently.

The generator never writes parquet, PMTiles, or tiles. It only produces JSON,
Markdown, PNG, and the copied styles.

## Catalog content

### Mirror status

`producer` and `host` are different organizations, so the catalog is a mirror
under `PORTO-CORE-053`. That requires a `via` link of type `text/html` to the
ANNCSU portal and an `updated` field on the root and on both collections. The
catalog makes no claim to be the authoritative copy.

Providers, in order, with exactly one `host` last as `PORTO-CORE-047` requires:

| Roles | Organization |
|---|---|
| producer, licensor | Agenzia delle Entrate |
| producer | ISTAT |
| processor | anncsu-open |
| host | Geobeyond |

### Root catalog

`catalog.json` carries a non-empty `title` and `description` (`PORTO-CORE-037`),
an `updated` field, and these links:

- `root`, pointing at itself, and no `parent`, since it is the root.
- `self`, absolute, to the public R2 base URL. `PORTO-CORE-081` recommends it,
  and it is what lets a validator resolve the relative references from the
  metadata alone.
- `child` to each collection, each with a `title` (`PORTO-CORE-039`).
- `agents` and `describedby` to the root `AGENTS.md` and `README.md`
  (`PORTO-CORE-061`, `PORTO-CORE-062`).
- `vcs` and `issues`, absolute, to the GitHub repository. Both are outside the
  published catalog, so they cannot be relative.
- `via` to the ANNCSU portal, since the mirror rule applies to the root too.

### Shared by both collections

- Extensions: Portolan v0.2.0, file v2.1.0, table v1.2.0, projection v2.0.0,
  web-map-links v1.3.0.
- `license: CC-BY-4.0` plus a `rel: license` link.
- Spatial extent from the real parquet bbox; temporal extent open-ended from the
  dataset date.
- A thumbnail and at least one MapLibre style asset carrying the `style` and
  `default` roles.
- A `rel: pmtiles` link to the shared PMTiles with `pmtiles:layers` set to
  `addresses`, read from the file header rather than hard-coded
  (`PORTO-FMT-011`, `PORTO-FMT-012`).
- `table:columns` on the collection itself (`PORTO-FMT-046`).

### `indirizzi`

A single-file collection: the parquet is a collection-level `data` asset and
there are no items (`PORTO-CORE-017`). The PMTiles is additionally registered as
a `visual` asset, which `PORTO-FMT-013` allows when the file is a genuine
distribution and not only a rendering derivative. Carries `table:row_count` and
`table:primary_geometry`.

### `indirizzi-h3`

A partitioned collection using the partition extension v1.0.0
(`PORTO-FMT-017`):

- `partition:scheme`: `hive`
- `partition:strategy`: `h3`
- `partition:keys`: one key, `h3_cell`, type `string`
- `partition:file_count`: the real tile count
- `partition:glob`: the HTTPS pattern over the published tiles

No items. `PORTO-FMT-022` advises against them for opaque schemes such as H3 and
for hundreds of partitions. `comuni-h3.json` is registered as a `metadata`
asset: it is the index the viewer uses to know which cells to fetch.

All tiles come from a single partition run, so they share one parquet schema as
`PORTO-FMT-021` requires. The tile schema is the main schema plus an `h3_cell`
VARCHAR column.

### The glob limitation

`partition:glob` is the normative bulk-access path, but a plain HTTPS glob
cannot be expanded, because HTTPS provides no listing. The spec acknowledges
this and permits bucket-native schemes.

The catalog uses the HTTPS form. It states the true location of the files and
stays readable in a browser. The README documents the two ways to expand it: the
`comuni-h3.json` index, which is how the viewer itself resolves cells without
listing, and the S3 endpoint for readers holding credentials.

### License caveat

The official ANNCSU pages cite EU implementing regulation 2023/138 on high-value datasets but do not state the licence in full. `CC-BY-4.0` is well founded, because that regulation mandates it for address data, and secondary sources confirm it. It was not found verbatim on the data owner's site.
The catalog declares `CC-BY-4.0` with a `rel: license` link to the open data page, and the README flags the point as unconfirmed.

## Workflow

A new `.github/workflows/build-catalog.yml`, triggered by `workflow_run` on
completion of "Update ANNCSU Data" and by `workflow_dispatch` for manual runs.
The job runs only when the triggering run concluded successfully, so a failure
upstream cannot produce a catalog describing stale data.

Checkout is full, with LFS and with the whole commit history (`fetch-depth: 0`
plus `filter: blob:none`, so commits and trees arrive but only HEAD's files are
materialised). The history matters because `updated` is read from the commit
that last touched the parquet: in a depth-1 clone that lookup returns HEAD,
`updated` moves with every unrelated commit, and the workflow commits a changed
catalog on every run, which is what happened on the first day. The generator
also refuses to trust a shallow clone and falls back to the dataset date. The
real bytes of the parquet and the PMTiles are needed for size and checksum, and
the tiles are needed for the count. That is
about 2.2 GB once a month. If it proves slow, the fallback is to download the
two large files from R2 and take the tile count from the bucket listing.

Steps:

1. Generate the catalog with `build_catalog.py`.
2. Validate with `rashid check data/ --schema`. This is the gate: on failure
   there is no commit and no upload. With the bytes present locally, `rashid`
   also confirms the declared checksums match the real files.
3. Commit when something changed, reusing the "check for changes" pattern from
   the existing workflow.
4. Upload only the catalog paths to R2, not all of `data/`. That means
   `catalog.json`, the root `README.md` and `AGENTS.md`, and the `indirizzi/`
   and `indirizzi-h3/` directories. The narrow scope keeps stray files out of a
   public bucket, and the data files are already synced by the upstream
   workflow.
5. After upload, re-run `rashid` with `--live` against the public base URL to
   check range requests and CORS, which `PORTO-CORE-045` requires of an asset
   host. This step reports but does not block, because a CORS problem is not a
   defect in the metadata just generated.

A concurrency group prevents overlapping runs. While the work is on a branch the automatic trigger does not fire, so testing uses manual dispatch.

## Testing

Tests are written before the implementation. A new `scripts/test_build_catalog.py` builds tiny fixtures on the fly: a parquet of a few rows, a real PMTiles produced with tippecanoe, and a handful of fake tile directories.

- **Conformance.** `rashid` runs over the generated fixture catalog and must report no findings. This is the spec's own validator rather than an interpretation of it, so it is the most valuable test in the file.
- **Determinism.** Two consecutive runs produce byte-identical output.
- **Checksums and sizes** match the real bytes and use the multihash prefix, not
  a bare sha256 string (`PORTO-CORE-029`).
- **Column drift.** The generator fails when the parquet and `columns.yaml`
  disagree in either direction.
- **Partition fields** match the tiles actually present, count included.
- **Link resolution** for every relative href, which is what breaks most easily
  when the directory structure changes.

## What conformance required of the pipeline

The first `rashid` run over the real catalog reported two errors and two
warnings, none of them in the generator.

The errors were in the data. DuckDB writes a GeoParquet **1.0.0** `geo` block
by itself, with no `covering` entry, so a reader cannot tell that the `bbox`
struct carries per-row bounds it may prune on. Portolan requires 1.1 or later
with that covering (`PTL-DAT-007`, `PTL-DAT-012`). The fix lives in
`enhance_parquet` in `scripts/update_data.py`: the Hilbert-sort `COPY` now
runs with DuckDB's automatic GeoParquet conversion disabled and writes the
1.1 block itself through `KV_METADATA`. Disabling the conversion matters
because otherwise DuckDB appends its own block next to ours and the file ends
up with two `geo` keys. The same change made the function idempotent, so it
can be re-run on its own output. A second pass through geoparquet-io was
measured as an alternative: correct, 23 seconds on the real file, but 6.5 GB
of peak memory and one more pass over a gigabyte.

The warnings were the README provenance heuristic (`PTL-FIL-005`), which
looks for English markers such as `source` and `origin`. The Italian text
now says "fonte originale", which satisfies it without switching language.

Two `info` findings remain and are expected: `PTL-PRO-002` asks for a
`canonical` link when the upstream publishes its own STAC catalog. ANNCSU does
not, so there is nothing to point at.

## Out of scope

- A `confini-comuni` collection for `istat-boundaries.parquet`. That file is not uploaded to R2 today, and its ISTAT licence needs separate checking.
- (Added on 2026-09-19, after the first release.) An English translation tree
  under `en/`, following the multilingual best practice: same ids, its own root
  with no parent, `alternate` links with `hreflang` in both directions, data
  and visual assets referenced in the Italian tree. Column descriptions carry
  a `description_en` in `columns.yaml`, and the build fails when one is
  missing. The same change added global statistics to descriptions and
  READMEs, recomputed from the parquet, and a `text/html` `alternate` link to
  the web viewer on the root and both collections.
- Migrating to `portolan push` or the template's `tools/publish.py`. The
  existing rclone step already does the job.
